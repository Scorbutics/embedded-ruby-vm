# Architecture - Embedded Ruby VM

## Three-Layer Design

```
Layer 3: High-Level Kotlin   (RubyInterpreterExtensions.kt, ScriptBatch.kt)
  |       Ergonomic APIs: executeBatch(), batch(), executeSync()
  v
Layer 2: Low-Level Kotlin    (RubyInterpreter.kt, RubyScript.kt)
  |       Direct wrappers over C API: enqueue(), execute(latch)
  v
Layer 1: C Core              (ruby-api-loader.h, ruby-interpreter.h, ruby-vm.c)
          Ruby VM integration: ruby_api_load(), ruby_interpreter_enqueue()
```

**Principle:** "Easy things should be easy, hard things should be possible."

- Layer 3 handles 80% of use cases (batch execution, simple workflows)
- Layer 2 enables custom synchronization with external systems (e.g., coordinating Ruby scripts + external DB via shared CountDownLatch)
- Layer 1 stays minimal: platform-agnostic Ruby VM integration, thread management, IPC, asset loading

**Don't flatten the layers.** Each serves a purpose. Layer 2 costs ~15 lines to maintain and removing it would force ugly workarounds for edge cases.

## Library Loading Architecture

The project supports both **static** and **dynamic** linking through a unified API in `ruby-api-loader.h`:

```c
int ruby_api_load(const char* lib_path, RubyAPI* api);
```

### Dynamic Loading (Default)

Used by Kotlin/Native and JNI platforms:

1. **Asset Extraction**: `libassets.a` extracts Ruby runtime to cache directory at first run
2. **Dependency Preloading**: `load_dependencies_from_file()` reads `libembedded-ruby.deps` and preloads `libruby.so` with `RTLD_GLOBAL`
3. **Main Library Loading**: `ruby_api_load()` uses `dlopen()` to load `libembedded-ruby.so`
4. **Symbol Resolution**: Function pointers populated via `dlsym()`

Key files:
- `libembedded-ruby.so` - Shared library with all Ruby VM functions exported
- `libembedded-ruby.deps` - Dependency list (generated by CMake)
- `libassets.a` - Static library for asset extraction
- `ruby-api-loader.h` - API loader with integrated dependency preloading

CMake uses `--whole-archive` to export symbols from `libruby-vm.a` into `libembedded-ruby.so`:
```cmake
if(UNIX AND NOT APPLE)
    target_link_libraries(embedded-ruby PRIVATE
        -Wl,--whole-archive logging ruby-vm -Wl,--no-whole-archive)
endif()
```

### Static Loading (Optional)

Enabled by defining `RUBY_STATIC` at compile time. Same `ruby_api_load()` signature — function pointers are assigned directly instead of via dlsym. Use for pure C apps or platforms without dynamic loading.

### Released Headers

A release ships `build/include` (the `packaged_headers` target): the headers of `include/public` and the generated `ruby-api-loader.h`, never `include/private`. Public headers include only public headers; the functions both loaders reach are declared in `ruby-api.h`, which the private headers include. `test_packaged_headers` builds a consumer against that directory alone.

### Architecture Constraints

- Ruby runtime (`libruby.so`) must be deployed at runtime, not hardcoded at build time
- `libembedded-ruby.so` cannot statically link Ruby (would create circular dependency)
- Asset system handles runtime extraction of Ruby and its dependencies

## Several Interpreters, One VM

CRuby runs one VM per process, initialized once (`ruby_init`). The simplest host runs one script in it — a game — until the process ends, and sends its output to a file. embedded-ruby-vm does more: several **interpreters** run scripts in the same VM at the same time. The case it exists for is PSDK-android's loading screen, a splash animated by a Ruby script (LiteRGSS) while another interpreter compiles the game, also in Ruby.

### How it works

```
host ──"<id> <script>"──▶ socket ──▶ dispatcher thread ──▶ worker thread (interpreter 1): splash loop
                                     (fifo_interpreter.rb)  worker thread (interpreter 2): compile
host ◀──"<id> <exit code>"── socket ◀──────────────────────  ...
```

- An interpreter is a Ruby thread of the shared VM, not a VM of its own. The dispatcher reads requests off a socket and hands each script to its interpreter's worker thread, created on first use.
- One interpreter runs its scripts one after the other; different interpreters run side by side. A script that never ends (a render loop) only holds its own interpreter.
- They share one GVL: Ruby code of two interpreters interleaves rather than runs in parallel. Long native work releases the GVL — LiteRGSS draws a frame outside it — so a splash keeps animating while a compile runs Ruby.
- They share the VM's global state: constants, `$stdout`, loaded files, the archive mount. Scripts meant to run beside others keep to what they own (the splash uses LiteRGSS primitives only, not the game's scripts).

### What it costs

Everything a process would give each script for free is rebuilt per interpreter:

- **Output**: `$stdout` is global, so each line is tagged with its interpreter and routed to that interpreter's listener (see [Logging Pipeline](#logging-pipeline)).
- **Completion**: "this script ended and its output was delivered" is an end-of-script sentinel per script, which needs the logging system's ordering across streams.
- **Lifetime**: an interpreter is stopped by a stop request its worker takes between two scripts — a render loop must end first (with LiteRGSS, the host asks its window to close).
- **Messages**: `VMHost` addresses events and messages per interpreter.

### Why not one script per process

The alternative keeps the VM simple: one process per script, its output a file or logcat, its end the process's. It works for one game at a time, and PSDK-android does run the game itself alone in its own process. The loading screen is what it cannot do: the splash would have to be native, or the compile a process of its own — a second VM boot, the archive mounted twice, the compile's progress and logs back through IPC — and iOS gives an app no general way to start processes of its own.

So the multi-interpreter machinery is what a Ruby loading screen costs. A host that runs one script per VM doesn't deal with it: it creates one interpreter, runs a script (`executeSync`, or a long-running one) and reads its listener.

## Logging Pipeline

Everything the scripts and the native code print reaches the host's listeners through the logging system (`core/logging/`), started with the first interpreter created with a `LogListener`.

```
Ruby $stdout / $stderr ─┐
VMLogger               ─┼─▶ 5 socket pairs ─▶ logger thread ─▶ dispatch queue ─▶ dispatch thread ─▶ per-interpreter LogListener
native fd 1 / fd 2     ─┘   (one per stream)   (read, cut      (FIFO, bounded)    (calls back)       native log (logcat, os_log...)
                                                into lines)                                           drain callbacks, sentinels
```

### Streams

Five streams, each its own socket pair: Ruby's stdout and stderr, `VMLogger`, and the process's native stdout and stderr (fd 1 / 2 are redirected into theirs; the original terminal descriptors are kept aside). The Ruby side tags each line with the id of the interpreter that wrote it, so a line reaches that interpreter's listener only; untagged native lines go to the first registered listener. `VMLogger` lines also carry their level, and carry the protocol lines: host events (`VMHost.emit`), the end-of-script sentinel, drain barriers.

Writers never wait on the logging system: a socket's buffer takes a line as soon as it is written, and only a full buffer (a reader stuck for long) would hold a writer back.

### Two threads

- **The logger thread** only reads: it waits in `select()` on the five sockets (and a wake pipe for its stop, so an idle app has no periodic wake-up), cuts the bytes into lines, parses their tags and queues them. It never runs host code, so it never stalls.
- **The dispatch thread** takes the queue in order and calls the listeners, the native log, drain callbacks and sentinel waiters.

They were one thread once: a listener that was slow, waited on another thread, or printed to stdout (which feeds the very sockets that thread had to empty) stopped the reading, the socket buffers filled up, and every `puts` of every interpreter waited — a deadlock as soon as the script held something the listener needed. Split, a slow listener only delays the delivery of the lines after it.

### Ordering and synchronization points

Lines of one stream arrive in order. Across streams, the logger thread reads at most a chunk per stream and `select()` round, so a line written later on a stream can be read before an earlier one on another. To keep the protocol lines meaningful, a `VMLogger` chunk ending a line first lets the other streams catch up: what they hold at that moment (everything written before that line) is read and queued ahead of it. Only what is already there is read — the other streams are never waited on, nor emptied for good.

Two synchronization points rely on it:
- **End-of-script sentinel** (`<<<LOGS_FLUSHED>>>`): written by the Ruby side after each script. A synchronous execution (`executeSync`, an interpreter's destruction) waits for it (up to 5 s), so it returns once the script's output was delivered, not while it is still in transit.
- **Drain barrier** (`logging_drain`): a marker the caller writes to the `VMLogger` stream, with a callback queued under the same number; the callback runs once every line queued before the marker was delivered. Used by the tests ("output delivered, now check it") through a test-only JNI entry.

### Bounds

- Log lines: up to 1024 queued; beyond, new ones are dropped with a periodic warning in the native log (a runaway producer must not eat the memory).
- Protocol items (drain barriers, sentinels) are never dropped: the host waits for them.
- Host events are never dropped either: beyond 256 queued, the logger thread waits for the dispatch thread — a listener that far behind holds back the scripts' logs and `VMHost.emit`.

### Listener contract

Listeners run on the dispatch thread and must not write to stdout / stderr: fd 1 / 2 feed the logging system itself, so each line a listener prints comes back to it as a new line — an endless loop, capped only by the queue bound (and a write to the full, non-blocking socket fails). Use the platform's log (`__android_log_print` / `android.util.Log`, `os_log`, `sd_journal_print`) or the original terminal descriptors (`logging_get_original_stdout_fd()` / `_stderr_fd()`, see `log-listener.h`).

## Design Decisions

### Why Kotlin Wrappers Instead of C Extensions?

C API stays minimal and focused on Ruby VM integration. Kotlin is better for high-level patterns (builders, sealed classes, extensions), easier to maintain/test, and avoids cross-platform C synchronization headaches.

### Why Hybrid Static/Dynamic Library Loading?

- **Runtime deployment requirement**: Ruby runtime extracted at runtime
- **Platform flexibility**: JVM/Android uses JNI+dynamic, Kotlin/Native uses cinterop+dlopen, pure C can use static
- **Transparent API**: Same function works for both approaches
- Trade-off: dynamic loading adds small runtime overhead but enables runtime asset extraction

## Cross-Platform Patterns

### Time APIs
- **JVM**: `System.currentTimeMillis()`
- **Native**: `clock_gettime(CLOCK_MONOTONIC, ...)` via `platform.posix`

### File APIs
- **JVM**: `java.io.File(path).readText()`
- **Native**: `kotlin.io.path.Path(path).readText()`

### Multi-platform APIs
- Use `actual`/`expect` for platform-specific implementations
- Platform-specific code: JNI for JVM, cinterop for Native
